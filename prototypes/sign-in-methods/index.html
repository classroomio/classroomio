Sign-in Methods

Every member already has a sign-in method recorded — password, Google, enterprise SSO, or token auth — but nothing in the product shows it. These screens surface it on the four places admins already look, plus the member's own account page. Built on the real packages/ui tokens. The engineering PRD lives at prd/sign-in-methods/README.md.

Every page has a theme toggle and cross-links, so you can click through the whole flow.

Badge vocabulary
Acme Okta

SSO. Named when the connection belongs to your org, generic SSO when it does not.

Token auth

Embedded partner access. Today these users are wrongly stored as password accounts.

Google

Google OAuth. Outlined, because the user manages it themselves.

Password

Email and password. The one admins are usually hunting for after an SSO rollout.

Lists show one badge — precedence SSO › Token auth › Google › Password. The member profile shows every method.

Three traps the PRD is built around.
Token-auth signup mints a real credential account row with a random password, so those users would be badged Password unless the row is retagged at the write site.
The login-link and token-exchange plugins raw-insert sessions, so Better Auth's databaseHooks never fire for them — and "view as student" must never overwrite the learner's record.
analytics_login_events is unique per user per day with onConflictDoNothing, so it can only ever hold the day's first login — which is why last-used lives on profile instead.
