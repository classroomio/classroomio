ClassroomIO · prototype/design

Zapier Integration

A V1 prototype for connecting ClassroomIO to Zapier: an org admin opens Zapier straight into a searchable app directory, authorizes access once, and manages the apps connected to ClassroomIO. Zaps themselves are created and managed on Zapier, not here. Grounded in the real IA already in the codebase: the Automation sidebar group (org-navigation.ts) and the OAuth-based connection model in prd/zapier/README.md, with the entry page inspired by Jotform's own integrations directory (see Design notes below).

Design notes

Built on app-theme.css, copied verbatim from prototypes/learning-paths, which mirrors the real packages/ui/src/index.css tokens. zapier.css adds only the patterns this flow needed (the directory landing hero, connection cards, grant tables, the app directory). Everything else reuses existing card, badge, table, tab, and form styles rather than inventing new ones. apps-catalog.js is the one place the 78 apps and their categories are defined, so the directory landing, the full App Directory, app-detail pages, and the connections page can never list different things for the same app. Every app mark renders through one ZI.badgeHTML() helper. Where brand-logos.js has a hand-built brand mark it draws that, otherwise a colored monogram.

Why the directory is the entry page, and why 78 apps
Zapier opens straight into a directory landing modeled on Jotform's own integrations directory: a heading, a functional search bar, and the three most recognizable integrations, so the page never feels like a half-empty marketing screen. A "Browse all apps" link leads to the full App Directory (sidebar search, category filters with counts, Popular/A–Z sort, "view more" pagination) for anyone who wants to look past the top three. Representing all 6,000+ Zapier apps isn't useful or buildable as a prototype. 78 real, named apps across the 15 categories Zapier actually organizes by, at least 5 per category, is enough to prove the directory holds up at a real-ish size. See README.md the README's app-count section for the full reasoning.

Why ClassroomIO has no Zap builder
ClassroomIO is the connection layer: it authorizes the organization, keeps the list of connected apps, and sends the admin to Zapier. Triggers, actions, field mapping, testing, publishing, and managing Zaps all happen on zapier.com, so the prototype never simulates them. That also matches the confirmed scope in prd/zapier/README.md: OAuth plus a dashboard page for grants.

Why every screen shows the full dashboard sidebar
Every screen except Authorize renders inside the same <aside class="sidebar"> a signed-in admin actually sees: Dashboard / Stats / Setup ungrouped at the top, then Content (Courses, Cohorts, Media, Tags, Widgets), People (Community, Audience), and Automation (MCP, API, Zapier), Settings, and the signed-in user pinned to the bottom. Zapier is the only working link (this prototype is scoped to this flow, not a full dashboard clone), and stays active throughout, pointing to index.html before a connection exists and zapier-connected.html after. The "Automation hub" screen (MCP/API/Zapier cards) still exists, one click away from the "Automation" breadcrumb on any Zapier screen, but it's no longer a required stop before reaching the directory. The goal isn't a standalone Zapier product, it's showing exactly where this feature sits in the real navigation and how an admin actually reaches it. See README.md “Sidebar” for the full reasoning, including why Authorize keeps its own minimal header instead.
