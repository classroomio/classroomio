ClassroomIO · prototype/design

Zapier Integration

A V1 prototype for connecting ClassroomIO to Zapier: an org admin discovers apps in a directory, authorizes access once, then builds automations where “this happens in ClassroomIO, so do this somewhere else”, without writing code. Grounded in the real IA already in the codebase: the Automation sidebar group (org-navigation.ts) and the OAuth-based connection model in prd/zapier/README.md, with the landing + directory structure inspired by SurveyMonkey's and Jotform's own Zapier pages (see Design notes below).

Design notes

Built on app-theme.css, copied verbatim from prototypes/learning-paths, which mirrors the real packages/ui/src/index.css tokens. zapier.css adds only the patterns this flow needed (the marquee, feature rows, grant tables, the app directory, the picker/field-mapping/stepper wizard). Everything else reuses existing card, badge, table, tab, and form styles rather than inventing new ones. apps-catalog.js is the one place the 77 apps, their categories, and their actions are defined (most fall back to one of 15 category-level default actions rather than 77 hand-written ones), so the directory, app-detail pages, and the builder can never list different things for the same app. Badges use a `color` on each app rendered through one `ZI.badgeHTML()` helper, not a per-app CSS class. That's the only way this stays sane past a handful of apps. brand-logos.js is a separate, landing-page-only set of 16 brand-colored marks for the marquee (see next).

Why a landing page + app directory, and why 77 apps
Screens 2 and 3 closely mirror the section rhythm and interaction patterns of two real Zapier integration pages: SurveyMonkey's landing (hero, connect bar, logo marquee, alternating value-prop rows, a numbered step-by-step walkthrough, integration highlights, FAQ) and Jotform's app directory (sidebar search, category counts, sort, card grid, "view more" pagination). Both are adapted to ClassroomIO's own visual language rather than copied, and trimmed of public-marketing-site elements (contact-sales forms, resource blog cards, mega-footers) that don't belong in an authenticated settings page. Representing all 6,000+ Zapier apps isn't useful or buildable as a prototype. 77 real, named apps across the 15 categories Zapier actually organizes by, at least 5 per category, is enough to prove the directory holds up at a real-ish size: search, category filters, and a genuinely working "view more apps" button that reveals the rest 18 at a time, with an explicit “that's every app in this sample” note and a link to Zapier's full catalog once you've seen them all. See README.md “Why 77 apps, not 6,000” for the full reasoning.

Why the builder lives inside ClassroomIO, not just a "Coming soon" link out
prd/zapier/README.md scopes v1 as OAuth plus a dashboard grant-management page, with the actual Zap built on zapier.com. That's still the safest v1 to ship. This prototype explores the fuller version worth planning toward. Zapier's Partner API and embedded editor (used by Webflow, Unbounce, and others) lets a partner render its own trigger/action picker, field mapping, and Zap on/off toggles natively. That's what screens 4 through 10 assume. See README.md for the full read on what's real today versus what this proposes.

Why every screen shows the full dashboard sidebar
Screens 1 through 13 (all but Authorize) render inside the same <aside class="sidebar"> a signed-in admin actually sees: Dashboard / Stats / Setup ungrouped at the top, then Content (Courses, Cohorts, Media, Tags, Widgets), People (Community, Audience), and Automation (MCP, API, Zapier), Settings, and the signed-in user pinned to the bottom. Zapier is the only working link (this prototype is scoped to this flow, not a full dashboard clone), and stays active throughout, pointing back to zapier-connect.html before a connection exists and zapier-connected.html after. The goal isn't a standalone Zapier product, it's showing exactly where this feature sits in the real navigation and how an admin actually reaches it. See README.md “Sidebar” for the full reasoning, including why Authorize keeps its own minimal header instead.
