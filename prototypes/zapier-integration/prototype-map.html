ClassroomIO · prototype/design

Zapier Integration

A V1 prototype for connecting ClassroomIO to Zapier: an org admin opens Zapier to an empty or non-empty Zaps view depending on whether anything's connected yet, discovers apps through a curated 20-app directory, authorizes access once, and manages the apps connected to ClassroomIO. Zaps themselves are created and managed on Zapier, not here. Grounded in the real IA already in the codebase: the Automation sidebar group (org-navigation.ts) and the OAuth-based connection model in prd/zapier/README.md, with the App Directory inspired by Jotform's own integrations directory (see Design notes below).

Design notes

Built on app-theme.css, copied verbatim from prototypes/learning-paths, which mirrors the real packages/ui/src/index.css tokens. zapier.css adds only the patterns this flow needed (empty/non-empty state cards, connection rows, the app directory, the Zapier-styled landing page). Everything else reuses existing card, badge, table, tab, and form styles rather than inventing new ones. apps-catalog.js is the one place the 20 apps and their categories are defined, so index.html's Non-Empty State, the full App Directory, and the Zapier landing page can never list different things for the same app. Every app mark renders through one ZI.badgeHTML() helper. Where brand-logos.js has a hand-built brand mark it draws that, otherwise a colored monogram.

Why index.html is an empty/non-empty state, and why 20 apps
Zapier opens into the org's own Zaps page, not a directory preview: an Empty State (no Zaps yet) or a Non-Empty State (already-connected apps), toggled by a prototype-only control. A "Connect Apps" CTA leads to the full App Directory (sidebar search, category filters with counts, Popular/A–Z sort, "view more" pagination) for discovering new integrations. Representing all 6,000+ Zapier apps isn't useful or buildable as a prototype, and neither is a generic large sample — the directory now carries exactly the 20 apps the integration research identified as genuinely relevant to a customer education platform. See README.md's "Why 20 apps" section for the full reasoning.

Why ClassroomIO doesn't connect or manage anything
ClassroomIO is already connected to Zapier — there's no separate "authorize your organization" step for a customer to complete inside ClassroomIO, and no connections/grants/revoke screen here either. Every CTA (Create a Zap, Connect Apps → an app, View Connection, Create More Zaps) either opens Zapier directly or passes through the Zapier-styled landing page on its way there. Triggers, actions, field mapping, testing, publishing, and managing existing connections all happen on zapier.com; the prototype never simulates or duplicates them.

Why every screen shows the full dashboard sidebar
Every screen renders inside the same <aside class="sidebar"> a signed-in admin actually sees: Dashboard / Stats / Setup ungrouped at the top, then Content (Courses, Cohorts, Media, Tags, Widgets), People (Community, Audience), and Automation (MCP, API, Zapier), Settings, and the signed-in user pinned to the bottom — except the Zapier landing page, which is deliberately styled as Zapier's own site (its nav, not ClassroomIO's) to signal the user has actually left ClassroomIO. Zapier is the only working sidebar link (this prototype is scoped to this flow, not a full dashboard clone), and stays active on every screen that keeps the sidebar, always pointing back to index.html. The "Automation hub" screen (MCP/API/ Zapier cards) still exists, one click away from the "Automation" breadcrumb, but it's not a required stop before reaching the directory. The goal isn't a standalone Zapier product, it's showing exactly where this feature sits in the real navigation and how an admin actually reaches it.
