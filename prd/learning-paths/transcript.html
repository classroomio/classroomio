Agent

The schema is committed and the PR is up, but the important part of this turn is your access question, so let me answer that first.

The two questions, and my answer

Should a path show a different progression or a single one? A single one. One enrolment, one progress record per learner per course, no matter how many paths contain it.

If they completed the course standalone, does the path treat it as done? Yes, immediately. It counts toward path completion and unlocks the next course.

The reason is that anything else means telling a learner "I know you finished this, but do it again where I can see it." That is the single most-complained-about behaviour in path features across LMSs, and it's worth being precise about who does it and who doesn't, because the two Courseras disagree with each other.

What the market actually does

Coursera Specializations share the learning record: courses common to two Specializations are *shared rather than copied*, and a course you finished on its own counts when you later enroll in the Specialization containing it. This is the consumer-facing product and it's the model I'd copy.

Coursera for Business learning paths do the opposite — their help docs say you must enroll in a course *through* the learning path for it to count toward completion. That's an artifact of enterprise reporting wanting attribution, and it's the anti-pattern here. It generates exactly the support ticket you'd expect: "I already did this course, why is it showing 0%."

Docebo learning plans don't store their own progress at all; plan status is derived by checking the enrollment status of each course in the plan. Same conclusion, reached from the data model side.

Moodle is the useful precedent for the *access* half rather than the progress half. A user can hold several user_enrolments rows in one course, one per enrolment method instance (manual, self, cohort sync). Access is the union of them, and disabling one method suspends its enrolments without touching the others.

Open edX links program enrollment to course enrollment by foreign key (ProgramCourseEnrollment → CourseEnrollment) rather than duplicating it, with at most one active program-course enrollment per user per course.

The consistent shape across all of them: progress is shared and single; access is plural and attributed.

How that lands in this codebase

Your instinct that enrolling in a path should create groupmember rows is right, and it's already the house pattern — cohorts do exactly this via insertGroupMembersOnConflictDoNothing. Course access stays isUserCourseMemberOrOrgAdmin, completely unaware that paths exist. Nothing about the course side needs to change.

The gap you identified is real: groupmember has no source, origin, or provenance column at all. So "who is in this course because of a path?" is currently unanswerable, and more urgently, "can I remove this person's access when they leave the path?" is unanswerable — which is how you end up either stranding orphaned enrolments or revoking access someone paid for directly.

I put the provenance on learning_path_member_course rather than adding a column to groupmember. Two columns carry it:

  • groupmemberId — which course enrolment this path step is attached to.
  • accessGrantedByPath — TRUE if path enrolment created that row, FALSE if the learner already had their own enrolment and the path adopted it.
That one boolean answers both directions. From inside a course, join groupmember → learning_path_member_course → learning_path to see who arrived via which path and who enrolled directly. From the path, know whether unenrolling is allowed to take anything away.

I kept it off groupmember deliberately. A single source enum column there would be wrong the moment a learner is in a course both directly and via two paths — one column can't hold three answers. The junction row is Moodle's multiple-enrolment-instances model, and it scales to cohorts later without a second refactor.

Revocation is conservative. Leaving a path sets accessRevokedAt and deletes the groupmember row only when accessGrantedByPath is TRUE *and* no other path holds a live grant. Someone who bought the course standalone never loses it by leaving a path. This also matches the existing house behaviour: removing a cohort member today deletes only cohort_member, never groupmember.

Sequential unlock gates the grant, not just the UI. Under sequentialUnlock, the groupmember row for course 4 isn't created until course 3 completes — locked means genuinely no access, not a hidden link. That's why groupmemberId is nullable.

The one honest cost of this design: a teacher looking at a course roster sees learners who never chose that course individually. That's why the reverse-lookup index on groupmemberId exists — the roster can label them "via Frontend Bootcamp" rather than leaving it mysterious. Schoox does the same thing with an explicit enrollment-source column showing values like "Assigned via Learning Path."

Here's the walkthrough you asked for, then what I documented.

First, a naming problem you should know about

Three things in this repo are called "cohort," and two of them are different products:

  • Cohort v1 — the shipped cohort / cohort_course / cohort_member tables. An org-level roster spanning many courses.
  • prd/course-cohorts/README.md — an 814-line PRD for something else entirely: *batches of one course*, each with its own group, with start/end dates. It is not built. The shipped cohort table has no startsAt/endsAt and isn't course-scoped.
That second PRD matters because it solves segmentation a completely different way: give each batch its own group, and since submissions, attendance, and lesson comments are already keyed on groupmember.id, they isolate for free. That's a legitimate alternative to my grant ledger, but it's the wrong tool for learning paths — a group per path would give a learner a second groupmember row and therefore a second set of submissions, which is exactly the forked progression we agreed to avoid. It also wouldn't isolate progress anyway, because lesson_completion is keyed on profileId, not groupmember.

So I put the new doc at prd/cohorts-v2/README.md and opened it with a table disambiguating all three, because someone will otherwise read the two cohort PRDs as versions of one thing.

How a cohort grants course access

Same route as today, one extra row. enrollCohortStudentsInGroups already calls insertGroupMembersOnConflictDoNothing; it gains a grant upsert in the same transaction:

groupmember       → (groupId, profileId, STUDENT)         -- unchanged
course_enrollment_grant → (groupmemberId, courseId, COHORT, cohortId)   -- new

If the learner already bought the course, the groupmember row is left completely alone and only the COHORT grant is added. That's the "adopt an existing enrollment" case, now a second grant instead of a boolean.

The timing question is the interesting one, and there's a trap already in the codebase. courseMemberMiddleware calls ensureProgramCourseAccess, which lazily creates groupmember rows for legacy program members *during the authorization check*. That means a GET request performs a transaction, and it can throw UPGRADE_REQUIRED (403) from a student-limit check — a read failing with a billing error. Don't copy that. Grants should be written eagerly at the triggering event: joining a cohort, enrolling in a path, or a course unlocking, each inside that service's existing transaction. Never in middleware.

That path also forced a schema addition: it creates enrollments with no grant behind them, which breaks the invariant the revocation logic depends on. I added PROGRAM to the enum so it can be recorded, and flagged retiring it as the better option.

Same route or a different one for the course page?

Same route, and no extra joins. This is the part worth being clear about: the grant table is not on the access read path at all. Access is still "does a groupmember row exist," one query, unchanged. Grants are only read when someone asks *why* — which is a teacher question, not a student one. A student loading a course page touches zero grant rows.

For the teacher's segmented views, add an optional filter to the existing endpoints rather than parallel routes:

?cohortId=<uuid>  |  ?learningPathId=<uuid>  |  ?source=COHORT

Two reasons. A per-segment route would have to be duplicated across the roster, gradebook, submissions, analytics, and attendance — that's the real maintenance explosion, not the join. And the repo rule that a route returns a single type is satisfied by a filter but violated by a route that returns a different shape depending on segment.

One genuine gotcha: a learner can hold several grants on one enrollment, so joining grants into the roster multiplies rows. Filter with EXISTS/IN as a semi-join, and if the roster should display origin, aggregate the sources rather than fanning out. I wrote that into both PRDs because it's the kind of thing that ships as a duplicate-rows bug.

Do middlewares need updating?

No, not for access. courseMemberMiddleware → isUserCourseMemberOrOrgAdmin reads groupmember OR org-admin. Because the invariant is "an enrollment exists exactly while it has ≥1 live grant," that predicate returns an identical answer before and after. Same for courseTeamMemberMiddleware and isCourseTeamMemberOrOrgAdmin. Sequential unlock also needs no change: a locked course simply has no enrollment yet, so the existing 403 is already correct.

Two things do need work, neither of them access logic:

  • The ensureProgramCourseAccess fallback must write a grant or be retired, as above.
  • Revocation is new service behaviour. Nothing in the codebase currently deletes a groupmember row on cohort removal, so the "delete when no live grants remain" step has to be added to removeCohortMemberService and removeCourseFromCohortService.

prd/cohorts-v2/README.md — the naming disambiguation, the four present-day consequences with the specific functions involved, the write sites and revoke sites as tables, the read-side filter, and a four-step migration. Here is the exact insert and remove, table by table.

When someone joins a path

One transaction. Five tables can be written; two of them are only written when they do not already exist.

| Table | What happens |
| --- | --- |
| learning_path_member | Insert one row, or clear removedAt if they were previously removed. This is the path roster. |
| learning_path_member_course | Insert one row per course in the path. First course NOT_STARTED; the rest LOCKED if sequential unlock is on, otherwise all NOT_STARTED. This is the path hub UI, not access. |
| organizationmember | Insert if they are not already in the org (after the student-limit check). |
| groupmember | Insert only for courses granted now, and only if the row is not already there. Sequential unlock: the first course. Otherwise: every course. This is what lets them open the course. |
| course_enrollment_grant | Upsert one LEARNING_PATH grant per granted course. This is why they have access. |

Nothing is written to lesson_completion or submission. That is why a course they already finished counts immediately: the rollup reads those existing rows, marks the course complete, and unlocks the next one — so someone who already did courses 1 and 2 lands on course 3.

When a later course unlocks (on completion of the previous one), that same write happens for that course: flip LOCKED → NOT_STARTED, insert groupmember if missing, upsert its grant.

When someone is removed from a path

One transaction. Two writes. Nothing is deleted.

| Table | What happens |
| --- | --- |
| course_enrollment_grant | Set revokedAt on this path's live grants for this learner. |
| learning_path_member | Set removedAt. |

groupmember is not touched. lesson_completion, submission, group_attendance, and the path certificate are not touched.

They lose course access because they no longer have a live grant, not because a row disappeared. If they also bought the course, that grant is still live and they keep the course. Re-enrolling clears removedAt and reactivates the grants, so progress is where they left it.

Why nothing is deleted

I was wrong earlier that we should delete groupmember when no live grant remains. Most FKs into that table (submission, group_attendance, lesson_comment, question_answer, course_newsfeed) have no ON DELETE, so Postgres refuses the delete for anyone who has ever submitted or been marked present. The one FK that *does* cascade — course_completion_record — would silently destroy compliance records. certificateEarnedAt lives on the row itself.

Deleting learning_path_member is equally unsafe: it cascades their per-course cache and their issued path certificate.

So access becomes "has a live grant", not "has a groupmember row". The two existing predicates (isUserCourseMemberOrOrgAdmin, isCourseTeamMemberOrOrgAdmin) each gain one indexed EXISTS. That is the only middleware change, and it is required rather than a preference.

The backfill I mentioned last turn is the same requirement, now for a clearer reason: once access means "has a live grant", any existing enrollment with no grant becomes invisible on deploy. That is why cohort, audience, invite, and program routes must write a grant — not because we are redesigning cohorts.

removedAt is now on learning_path_member in schema.ts. Pushed to feats/learning-paths; #1098 updated. Still no migrations.
