# PRD: Non-Technical Editing Layer for Help Docs

## 1. Context & Problem

Our help documentation (how-to guides and support content) lives as Markdown/MDX files inside our product repository. The docs site is built with **Blume**, which infers routing, navigation, and page metadata directly from the file system under the content root (`docs/` by default). There is no central navigation manifest — each `.md`/`.mdx` file becomes a page, ordering comes from numeric filename prefixes, and frontmatter at the top of each file carries page metadata (title, description, etc.).

Today, a writer or non-technical contributor who wants to update a help doc must clone the repo, install dev tooling, run the local environment, edit raw Markdown, and open a pull request via Git. This is too much overhead for people whose job is writing, not engineering. It creates a bottleneck where docs updates depend on developer time.

## 2. Goal

Give non-technical writers a **web-based editing experience** for the help docs that:

- Requires no local repo clone, no dev environment, and no Git knowledge.
- Writes changes back to the existing Markdown/MDX files in the repo.
- Routes every change through our existing review → merge → deploy pipeline, unchanged.
- Leaves Blume's build and deploy process completely untouched (docs stay file-based in the repo; Blume regenerates nav/routing on build as it does now).

The target workflow:

```
Writer → Web CMS → Commit/PR to GitHub → Review → Merge → Blume build → Deploy
```

## 3. Non-Goals

- Migrating content out of the repo into an external database or headless CMS store. Content **must remain** as `.mdx` files in the repo (Blume depends on this).
- Replacing or modifying the Blume build or the Cloudflare deploy pipeline.
- Letting writers create new top-level sections or reorganize site structure (both require a `navigation.sidebar` edit in `blume.config.ts`). Structural changes remain a developer task in v1.
- Bringing `apps/docs` (developer docs) into scope for v1.
- Building a custom editor from scratch. Use an existing, maintained, Git-backed CMS.

## 4. Constraints & Environment (confirmed from repo investigation)

- **Two apps with distinct audiences:**
  - `apps/help` (`@cio/help`, Cloudflare Worker `cio-help`, served at `classroomio.com/help`) — the **user-facing help center** for people running an academy (courses, enrollment, publishing). **This is the target of this PRD** — its writers are the non-technical contributors we're unblocking.
  - `apps/docs` (`@cio/docs`, Cloudflare Worker `cio-docs`, served at `classroomio.com/docs`) — **developer-facing docs** (self-hosting, API, contributing). Out of scope unless we later choose to extend (see section 11). Same technical pattern, but a different, more technical author audience.
- **Both are static Astro sites** generated by Blume (`blume@1.2.0`, third-party npm package by Hayden Bleasel — NOT a local monorepo package), reverse-proxied by `apps/website` at `/help/*` and `/docs/*`.
- **Content root:** `apps/help/content/help` (set via `content.root: 'content/help'` in `apps/help/blume.config.ts`). (For reference, docs uses `apps/docs/content/docs`.) NOT `docs/`.
- **File format:** 100% `.mdx`, zero `.md`. New pages should be `.mdx`.
- **Ordering & navigation — CRITICAL, differs from earlier assumption:** Both apps define an **explicit `navigation.sidebar` array in `blume.config.ts`**. This is the highest-priority mechanism in Blume's ordering precedence and **overrides filename order, `meta.ts`, and frontmatter `sidebar.order`.** There is **no numeric-filename-prefix convention** and **no `meta.ts` files** in either app. Practical consequence: **a page a writer adds via the CMS will not appear in the sidebar until `blume.config.ts`'s `navigation.sidebar` array is updated to include it.** This is the single most important design constraint — see section 6.4/6.5.
- **Metadata (real frontmatter fields observed):** `title` (always), `description` (always), `sidebar.order` (numeric; used in ~25/39 help files but moot for top-level order since the explicit sidebar wins), `sidebar.label` (label override), and a custom `last_reviewed` field (added via `frontmatter.extend` with a Zod schema, read by `scripts/check-stale-docs.mjs` for staleness checks). There is **no `slug` field** — slugs derive from file path. There is **no `draft` field in use** — confirm whether Blume's `draft` frontmatter is supported by this version before relying on it (see section 6.3).
- **MDX everywhere:** since every page is `.mdx` and may use Blume MDX components, the in-CMS Markdown editor cannot reliably render pages — the PR preview (section 6.6) is essential, not optional.
- **Version control:** GitHub. Default branch is `main`. The existing PR review pipeline must be reused as-is.

### 4.1 Hosting & deploy (critical — this shapes auth and preview)

- **Hosting:** Cloudflare Workers **Static Assets** (not Cloudflare Pages, not Netlify, not Vercel, not Railway). Each site is prerendered by `blume build`, packaged by the **per-app** script `apps/help/scripts/package-assets.mjs` (which moves Blume's `dist/` into `build/help/`), and served as static files with no SSR. Note: this is a per-app script — there is no root-level `scripts/package-assets.mjs`.
- **Production serving:** `classroomio.com/help/*` and `/docs/*` are proxied by the marketing site (`apps/website/src/hooks.server.ts`) to the `cio-help` / `cio-docs` Workers.
- **Deploy mechanism:** **not** GitHub Actions. Deploy happens via local `wrangler deploy`, or via Cloudflare's own connected-repo Git integration — evidenced by the `CLOUDFLARE_DOCS_DEPLOY_HOOK` webhook secret that an existing workflow pings after the OpenAPI spec changes. Practical implication: **merging a PR to `main` is what triggers the production rebuild.** The CMS editorial workflow must therefore open PRs against `main`.
- **PR previews:** none exist today for `apps/help` / `apps/docs`. The only preview-deploy workflow in the repo (Railway) is scoped to dashboard/api. Cloudflare Workers Builds *can* generate per-branch preview URLs, but that is configured in the Cloudflare dashboard (not visible in-repo) and must be explicitly enabled or otherwise built — do not assume it exists.

### 4.2 Existing CI / governance constraints

- **CLA gate:** `CONTRIBUTING.md` requires a CLA sign-off before merge (label-gated; only one authorized approver verifies). CMS-authored PRs will be subject to this — confirm how internal writers are handled (e.g. pre-signed / exempt).
- **Workflow-safety rule:** `CONTRIBUTING.md` explicitly warns against `pull_request_target` workflows that check out or build untrusted PR code. Any new CI added for previews/validation must respect this — prefer `pull_request` with no privileged secrets on untrusted code, or gate carefully.
- **Existing docs CI is advisory-only:** `docs-validate.yml` runs `blume validate` (internal link/anchor checks) + Vale prose linting on `apps/help/content/help` and `apps/docs/content/docs`, on PRs. All steps are `continue-on-error: true` (advisory). It correctly uses plain `pull_request` (not `pull_request_target`), so it already handles untrusted-fork safety. `docs-label.yml` (which does use `pull_request_target`) only applies a `needs-docs-review` label and builds no content. CMS PRs will trigger both; writers should understand these checks are advisory/non-blocking.
- **No relevant secrets/OAuth exist yet:** no Netlify Identity, no OAuth proxy, no GitHub App credentials anywhere in the repo. The OAuth backend is a from-scratch decision. Existing Cloudflare secrets (`CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, R2 keys, the deploy hook) are scoped to R2/spec uploads, not to a CMS auth flow.

## 5. Proposed Solution

Adopt a **Git-backed CMS** — recommended **Sveltia CMS** (a faster, actively maintained drop-in replacement for Decap CMS, sharing Decap's config format). The CMS is a web app that:

1. Reads the Markdown/MDX files under the app's content root (`apps/help/...`).
2. Presents writers with a form (frontmatter fields) plus a rich Markdown editor (page body).
3. On save, commits to a branch and opens a Pull Request **against `main`** via GitHub's API.
4. The PR flows into the existing review + merge pipeline. Merging to `main` triggers Cloudflare's connected-repo rebuild (or `wrangler deploy`), which reruns `blume build`.

Writers authenticate via GitHub OAuth (backed by a small OAuth proxy running as its own Cloudflare Worker, or a GitHub App — see section 7) and never touch a local Git checkout.

## 6. Functional Requirements

### 6.1 Editing
- Writers can browse existing help-center pages and open any page for editing in a browser.
- Writers edit page **body** in a rich editor. Note: pages are `.mdx` and may contain Blume MDX components; the editor should preserve MDX/JSX it doesn't understand rather than corrupt it (see 6.7). For component-heavy pages, rely on the PR preview.
- Writers edit **frontmatter fields** through form inputs: `title` and `description` (both required), optional `sidebar.label`, and `last_reviewed`. Do **not** invent fields Blume's schema won't accept — the frontmatter schema is defined per app (`frontmatter.extend`) and unknown keys may fail `blume validate`.
- Writers can create **new pages** within existing sections (existing content subfolders such as `get-started/`, `build-a-course/`, etc.).
- Image uploads are supported and land in the correct in-repo asset path for `apps/help`, referenced with the correct public path.

### 6.2 Publishing workflow
- Saving a change creates a **Pull Request** (editorial workflow / `publish_mode: editorial_workflow`) against `main`, not a direct commit.
- Each PR is reviewable and mergeable through the existing GitHub process, and will trigger the advisory `docs-validate.yml` (Vale + `blume validate`) and `docs-label.yml` checks.
- On merge to `main`, the Cloudflare rebuild runs with no manual steps.

### 6.3 Drafts
- **Do not assume `draft: true` works.** Unlike the earlier assumption, no `draft` frontmatter is currently in use, and it is not confirmed supported in `blume@1.2.0`. The agent must verify Blume's draft behavior for this version before exposing a draft control. If unsupported, use the editorial-workflow PR itself as the "draft" state (work-in-progress lives in the unmerged PR) rather than a frontmatter flag.

### 6.4 Ordering (REVISED — this is the crux)
- **The earlier numeric-filename-prefix assumption is wrong and must be discarded.** Neither app uses numeric prefixes or `meta.ts`. Sidebar order and membership are controlled by an **explicit `navigation.sidebar` array in `apps/help/blume.config.ts`**, which overrides frontmatter `sidebar.order`.
- **Direct consequence:** a new page created via the CMS **will not appear in the sidebar until `navigation.sidebar` in `blume.config.ts` is updated.** Editing an existing page's body/frontmatter works fine with no config change; only *adding* or *reordering* pages requires a config edit.
- The agent must choose and document a handling strategy for this, e.g.:
  - (a) **Writers edit existing pages freely via the CMS; adding/reordering pages remains a small developer step** (update `navigation.sidebar`). Simplest and safest for v1.
  - (b) Expose `blume.config.ts`'s sidebar as a CMS-editable data file so writers can register/reorder pages — significantly more complex and risky (it's TypeScript, not data), so only if strongly justified.
  - Recommend (a) for v1 and note (b) as a possible follow-up.

### 6.5 Structure
- Map the CMS to the existing `content/help` folder structure — one CMS collection per top-level section (`get-started`, `build-a-course`, `live-classes`, `enrollment-and-students`, `publish-your-academy`, `organization-and-team`, `reference`) — so writers add/edit pages within existing sections.
- Creating new top-level sections is out of scope for writers (it requires both a new folder and a `navigation.sidebar` edit) and remains a developer task.

### 6.6 Preview
- **No PR preview exists today for these apps — one must be built.** Provide a per-PR/per-branch preview that runs the app's full build (`blume build && node apps/help/scripts/package-assets.mjs`) so writers see real rendered Blume/MDX output before merge. Options to evaluate:
  - **Enable Cloudflare Workers Builds branch previews** for `cio-help` in the Cloudflare dashboard (preferred — consistent with the existing deploy path). Confirm whether the connected-repo integration already emits non-production branch preview URLs.
  - **Or** a new GitHub Actions job that builds and deploys a preview — following the pattern `docs-validate.yml` already uses (plain `pull_request`, no privileged secrets exposed to fork code).
- The preview is essential because every page is `.mdx` and the in-CMS editor cannot reliably render Blume MDX components.

### 6.7 MDX integrity
- Because content is 100% `.mdx`, the CMS must round-trip MDX/JSX and existing frontmatter (including `last_reviewed`, `sidebar.*`) without stripping or mangling it. Validate that a no-op CMS edit produces a diff limited to the intended change and still passes `blume validate`.

## 7. Authentication

- Writers log in via **GitHub OAuth** through the CMS ("Login with GitHub").
- **Netlify Identity is NOT an option** — hosting is Cloudflare, and no Netlify infra exists. Do not propose it.
- Implement the OAuth backend as one of (evaluate and pick one):
  - **A small OAuth proxy deployed as its own Cloudflare Worker.** This is the recommended default — it matches the existing Cloudflare-first infra and keeps everything on one platform. Sveltia/Decap document the GitHub-backend proxy contract; several one-file Worker implementations exist.
  - **A GitHub App** granting scoped repo access.
- Register a GitHub OAuth App / App with the callback URL pointing at the proxy Worker. Store client secret as a Worker secret (do not commit).
- Writers should be granted only the repo access the CMS requires; they must not need a local Git setup. Confirm how this interacts with the CLA gate (section 4.2) for internal writers.

## 8. Edge Cases & Notes for the Agent

- **Navigation is config-driven, not filesystem-driven:** the biggest gotcha. Editing existing pages needs no config change; adding or reordering pages requires updating `navigation.sidebar` in `apps/help/blume.config.ts`. Design around this (see 6.4).
- **All pages are `.mdx`:** the CMS must round-trip MDX/JSX and existing frontmatter (`last_reviewed`, `sidebar.order`, `sidebar.label`) without corruption, and edits must still pass `blume validate`.
- **New pages are `.mdx`** (both apps are 100% `.mdx`).
- **Frontmatter schema is enforced:** each app extends Blume's frontmatter schema via `frontmatter.extend` (Zod). Don't introduce fields the schema rejects, or `blume validate` may flag them.
- **Draft support is unverified** in `blume@1.2.0` — verify before exposing a draft control; otherwise use the unmerged PR as the draft state.
- **Stale-README caution:** `apps/help/README.md` currently claims the help app has *no* explicit `navigation.sidebar` and infers nav from the folder tree. This is **out of date** — the current `blume.config.ts` *does* define an explicit sidebar. Trust the config, not the README. (Worth fixing the README as part of this work.)

## 9. Deliverables

An agent implementing this PRD should produce:

1. A Git-backed CMS (Sveltia recommended, Decap acceptable) hosted at an internal URL, targeting `apps/help` and its `content/help` root.
2. A CMS config with **one collection per top-level section** (`get-started`, `build-a-course`, `live-classes`, `enrollment-and-students`, `publish-your-academy`, `organization-and-team`, `reference`), fields for `title`, `description`, optional `sidebar.label` and `last_reviewed`, and a body editor that round-trips `.mdx` + all existing frontmatter without corruption.
3. Media upload configured to the correct `apps/help` asset path and public path.
4. Editorial (PR-based) workflow enabled, opening PRs against `main`.
5. GitHub OAuth working end-to-end via an OAuth proxy Worker (or GitHub App) — no Netlify Identity.
6. A per-PR preview that runs the full build (`blume build && node apps/help/scripts/package-assets.mjs`), following the plain-`pull_request` pattern `docs-validate.yml` uses.
7. A documented strategy for the add/reorder-page → `navigation.sidebar` gap (6.4), recommending the v1 approach.
8. A short writer-facing guide: log in, edit a page, submit for review, upload an image — noting that adding/reordering pages currently needs a developer step, and that Vale/label checks are advisory.
9. (Nice-to-have) Fix the stale `apps/help/README.md` nav description.

## 10. Success Criteria

- A non-technical writer can, in a browser and with no Git tooling: edit an existing help page, upload an image, and submit — resulting in a PR against `main`.
- The PR renders correctly in a deploy preview, passes (or advisory-flags) the existing checks, and merges through the normal process.
- Merging to `main` triggers the Cloudflare rebuild with no developer intervention.
- Editing existing pages requires no `blume.config.ts` change; the add/reorder-page limitation is clearly documented and handled per 6.4.
- No changes were required to Blume's build or the Cloudflare deploy setup beyond CMS + preview wiring.
