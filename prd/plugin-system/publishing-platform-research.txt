ClassroomIO Plugin Publishing Research
=======================================

Decision status
---------------

The earlier quarantine-upload recommendation in this research was superseded
by the PR-first release model. ClassroomIO now reviews plugin source through
pull requests to the official `classroomio-plugins` repository. Only protected
post-merge CI may build production artifacts, upload immutable assets, and
register a catalog release. Contributors do not receive upload credentials or
a `plugin:publish` token.

Purpose
-------

This document compares the publishing and review workflows used by Figma,
Shopify, Moodle, Visual Studio Code, and Google Chrome. It then maps the
patterns to the proposed ClassroomIO plugin marketplace workflow.

The central conclusion is that developers generally submit a built artifact
through a platform API or dashboard. A GitHub repository is usually optional
or used for source transparency and automation; it is not normally the public
marketplace submission mechanism.


Executive comparison
--------------------

Figma
  Submission: Publish through the Figma product UI to Figma Community.
  Review: Public Community plugins go through Figma review before listing.
  GitHub: Optional; not the submission channel.
  Internal path: Internal organization plugins can be published without
                 Community review.

Shopify
  Submission: Submit a production app and listing through the Partner
              Dashboard.
  Review: Automated pre-submission checks followed by human App Store review.
  GitHub: Optional; the deployed app and submitted listing are the review
          target.
  Internal path: Development, custom, and limited-visibility distribution
                 paths exist outside the public App Store.

Moodle
  Submission: Upload a plugin ZIP to Moodle Marketplace with metadata,
              documentation, screenshots, and setup information.
  Review: Automated archive/CI checks plus manual review.
  GitHub: Strongly encouraged and useful for source transparency and CI, but
          Moodle Marketplace still requires an explicit release submission.
  Internal path: Developers may self-host plugins without submitting them to
                 the public directory.

Visual Studio Code
  Submission: Package a VSIX and publish with `vsce` or upload it through the
              Marketplace publisher page.
  Review: Package validation, publisher controls, signing, automated and
          ongoing security/policy enforcement. The public documentation does
          not describe a manual approval queue for every extension.
  GitHub: Optional; commonly used for repository links and README metadata.
  Internal path: Private marketplaces and manually distributed VSIX files.

Google Chrome
  Submission: Upload a ZIP extension package through the Chrome Web Store
              Developer Dashboard.
  Review: Automated and manual review for policy, safety, privacy, quality,
          and malware concerns. Existing items are periodically re-reviewed.
  GitHub: Optional; not the canonical submission channel.
  Internal path: Enterprise/private distribution and policy exceptions for
                 enterprise extensions.


1. Figma
--------

Figma publishing workflow

Figma developers select a plugin in Figma, choose Publish, select Publish to
Community, provide listing details, add artwork and support information, and
submit the plugin for review. Figma manages the release artifact and listing
behind the product UI. Developers do not open a pull request to Figma and do
not receive direct object-storage credentials.

Figma review workflow

Before a plugin is listed in Figma Community, it enters review. Figma notifies
the creator of the decision. A rejected plugin can be corrected and submitted
again. The review guidelines cover:

  - Quality, completeness, usability, and performance
  - Accurate descriptions and screenshots
  - Trust and safety
  - Privacy and legal obligations
  - Support contact information
  - Compliance with Figma APIs and platform rules

Figma internal workflow

Figma supports publishing plugins internally to an organization without public
Community review. If the publisher changes an internal plugin to public,
Figma requires the Community review process. This is a useful distinction for
ClassroomIO between organization-only releases and public marketplace releases.

Figma update workflow

Material changes can require review. Creators can update or cancel a pending
submission, and Figma can require later reviews as policies evolve.

Official sources

  https://help.figma.com/hc/en-us/articles/43029200314135-Publish-generative-plugins-to-the-Figma-Community
  https://help.figma.com/hc/en-us/articles/360039958914-Plugin-and-widget-review-guidelines
  https://help.figma.com/hc/en-us/articles/4404228629655-Create-internal-plugins-for-an-organization
  https://help.figma.com/hc/en-us/articles/4404228724759-Manage-plugins-and-widgets-in-an-organization


2. Shopify
----------

Shopify submission workflow

Shopify developers prepare a production app in the Partner Dashboard, then
complete the App Store listing and submission form. The submission includes
configuration, application URLs, compliance webhooks, app icon, contacts,
protected-data declarations, testing instructions, and listing information.

Before submission, Shopify requires automated checks for common errors. The
developer must fix failed checks before the app enters review. Shopify also
expects testing on development stores and production-ready functionality.

Shopify review lifecycle

The documented state sequence is approximately:

  Draft -> Submitted -> Reviewed -> Published

An app can be paused if reviewers cannot test it or if blocking issues exist.
The reviewer can request fixes, after which the developer resubmits. Shopify
reviews the live app as well as the listing and submitted test credentials.

Shopify review concerns include:

  - Functional and usable UI
  - Correct authentication and API behavior
  - Billing behavior
  - Data protection and compliance
  - Accurate listing information
  - Test credentials and a demo screencast
  - Compliance with Shopify policies

GitHub is not required. A source repository may help with development, but the
review target is the production app and its submitted metadata. A GitHub PR
would not prove that the deployed app is the artifact users will run.

Shopify also performs quality checks after publication, so approval is not a
permanent exemption from later review.

Official sources

  https://shopify.dev/docs/apps/launch/app-store-review/submit-app-for-review
  https://shopify.dev/docs/apps/launch/app-store-review/pass-app-review
  https://shopify.dev/docs/apps/launch/app-store-review/review-process
  https://shopify.dev/docs/apps/launch/shopify-app-store/app-store-requirements
  https://shopify.dev/docs/apps/launch/app-store-review/app-quality-checks


3. Moodle
---------

Moodle submission workflow

Moodle Marketplace accepts a plugin ZIP together with plugin metadata,
documentation, installation instructions, screenshots, and related listing
information. The current Moodle FAQ describes this process:

  1. Sign in to Moodle Marketplace.
  2. Choose Submit a plugin.
  3. Upload a valid ZIP with a unique component name.
  4. Add details, documentation, installation/setup information, and images.
  5. Complete automated archive validation and Moodle Plugin CI tests.
  6. Enter the review queue.

Moodle validation workflow

Moodle combines automatic and manual validation. The legacy official
validation documentation describes the states as:

  Plugin submission -> Waiting for approval -> Approved

A submission can be returned as needing more work and then resubmitted.
Automated checks inspect ZIP structure, naming, required files, compatibility,
and plugin conventions.

GitHub's role in Moodle

Moodle strongly encourages a public source repository, usually GitHub. It is
useful for collaboration, issue tracking, source transparency, and CI. However,
Moodle does not automatically pull releases from GitHub. Developers explicitly
release a version through the Moodle plugin platform.

Moodle's plugin API can accept a ZIP upload, base64 ZIP contents, a ZIP URL, or
version-control metadata such as a repository URL and tag. GitHub Actions can
automate a release after a tag is pushed, but the Marketplace remains the
registry, validator, and distribution system.

Moodle private/self-hosted workflow

Moodle documentation makes clear that a developer does not have to submit every
plugin to the public directory. A plugin can be hosted and distributed by the
developer directly.

Official sources

  https://docs.moodle.org/503/en/Plugins_FAQ
  https://docs.moodle.org/dev/Plugin_validation
  https://docs.moodle.org/dev/Plugin_contribution
  https://docs.moodle.org/dev/Plugins_directory_API


4. Visual Studio Code
---------------------

VS Code publishing workflow

VS Code extensions are packaged as VSIX files. Developers can publish with:

  vsce publish

or package first and upload manually:

  vsce package

The VS Code Marketplace owns publisher identity, hosting, management, and
extension signing. The `vsce` tool performs packaging and pre-publish checks.

Validation and security

The publishing tool checks package constraints, including restrictions on
certain SVGs and remote images. The Marketplace signs published extensions,
and VS Code verifies the signature when installing an extension. The ecosystem
also uses automated and ongoing security/policy enforcement.

The public documentation does not describe a manual approval decision for every
extension in the same way as Figma, Shopify, or Moodle. VS Code is closer to an
automated validation plus ongoing enforcement model.

GitHub's role in VS Code

GitHub is optional. If an extension declares a public repository, the
Marketplace can use it for repository links and README metadata. The actual
submission is still the VSIX artifact, not a GitHub pull request.

Private distribution

Extensions can be installed manually from a VSIX or distributed through a
private Marketplace for an organization.

Official sources

  https://code.visualstudio.com/api/working-with-extensions/publishing-extension
  https://code.visualstudio.com/docs/configure/extensions/extension-marketplace
  https://code.visualstudio.com/api/references/extension-manifest
  https://code.visualstudio.com/api/working-with-extensions/continuous-integration


5. Google Chrome
---------------

Chrome Web Store submission workflow

Chrome extension developers prepare a ZIP package, register a developer
account, and upload the item through the Chrome Web Store Developer Dashboard.
The extension manifest and listing metadata are submitted through that system;
developers do not open a pull request to Chromium or upload directly to a
Google-controlled storage bucket.

Chrome review workflow

Chrome uses a combination of automated and manual systems. The review checks
the extension against the Chrome Web Store Developer Program Policies and can
result in approval, rejection, warnings, takedown, or malware enforcement.
Chrome also periodically reviews already-published items.

Chrome review concerns include:

  - Safe, useful, and honest functionality
  - A narrow single purpose
  - Permission minimization and data-use disclosure
  - Privacy policy accuracy
  - No deceptive installation or review manipulation
  - No spam, malware, or harmful behavior
  - Accurate name, description, category, icon, screenshots, and developer data
  - Manifest V3 and technical requirements
  - Developer contact information and two-step verification

Chrome's documented publishing-review outcomes are:

  - No violations: approved and publishable
  - Policy violation: rejected with an explanation
  - Severe violation or malware: stronger enforcement, including removal

Chrome updates

An update is submitted for review separately. Existing users continue running
the current version until the new version passes review and is published. Chrome
also supports deferred publishing after review, allowing a publisher to stage a
release before making it live.

GitHub's role in Chrome

GitHub is optional and is not the canonical submission mechanism. The artifact
uploaded to the Chrome Web Store is what is reviewed and distributed.

Enterprise distribution

Enterprise extensions can be distributed through managed/private channels, and
some enterprise extensions receive policy exceptions such as the single-purpose
rule.

Official sources

  https://developer.chrome.com/docs/webstore/prepare
  https://developer.chrome.com/docs/webstore/review-process
  https://developer.chrome.com/docs/webstore/program-policies
  https://developer.chrome.com/docs/webstore/program-policies/policies
  https://developer.chrome.com/docs/webstore/update
  https://developer.chrome.com/docs/webstore/program-policies/terms


Cross-platform patterns
-----------------------

The recurring architecture is:

  1. Developer-owned source project
  2. Deterministic distributable artifact
  3. Platform-side automated validation
  4. Submission record and review state
  5. Human review for public/community distribution where required
  6. Separate internal/private distribution path
  7. Ongoing post-publication review and enforcement

GitHub usually provides source transparency, issue tracking, documentation,
collaboration, and CI. It is not usually the artifact registry or the final
distribution authority.


Do platforms submit directly to a bucket?
-----------------------------------------

Developers generally do not see or control the platform's object-storage
bucket. The platform hides storage behind a UI or API. The effective flow is:

  CLI/UI -> platform API -> private artifact storage -> validation -> review
       -> production storage/CDN -> user installation

Moodle exposes the ZIP concept directly and VS Code exposes the VSIX concept.
Figma and Shopify abstract the artifact storage more completely. All four
patterns are compatible with a private quarantine bucket internally.


Adopted ClassroomIO model
-------------------------

Public/community plugin flow

  Contributor fork
      -> plugin source and manifest
      -> pull request to classroomio-plugins
      -> untrusted checks, tests, package validation, and reviewer artifact
      -> source review and approval
      -> merge to protected main
      -> protected CI rebuilds and proves the digest is deterministic
      -> protected CI uploads immutable digest-qualified assets to production R2
      -> protected CI registers the release and its provenance in ClassroomIO

Local development flow

  Plugin developer
      -> npm run build
      -> pnpm run pack
      -> pnpm run seed -- <plugin-path> --org <organization-id>
      -> organization-scoped development installation

Local seed uses an organization API key with `plugin:development` scope. It is
not a publication mechanism and cannot create a public catalog release.

Canonical source repository

The official `classroomio-plugins` repository is the single source of reviewed
production plugin code. A plugin manifest may still link to the original
author's homepage, issue tracker, or upstream project, but the reviewed source
and lockfile merged into the official repository are authoritative.

Suggested metadata:

  {
    "repository": {
      "type": "git",
      "url": "https://github.com/example/classroomio-plugin"
    },
    "homepage": "https://example.com/plugin",
    "bugs": {
      "url": "https://github.com/example/classroomio-plugin/issues"
    }
  }

Protected CI packages the exact reviewed merge commit. Pull-request artifacts
exist only for reviewer inspection and expire; contributors never upload to
the production bucket.

Recommended provenance record

For stronger supply-chain security, store the following with every submission:

  - Artifact SHA-256 digest
  - Repository URL
  - Git commit SHA
  - Protected workflow run URL
  - Build tool and SDK versions
  - Dependency lockfile hash
  - Automated validation results
  - Review history in the merged pull request

This ties every production digest to reviewed source and a protected workflow.


Recommended ClassroomIO policy
------------------------------

Community plugins require:

  - A pull request to the official plugin repository
  - Valid manifest
  - Committed dependency lockfile and exact public dependency versions
  - Automated validation
  - Human source review
  - Support contact
  - Privacy/data policy
  - A version bump for every changed release

Local development requires:

  - Organization-scoped credentials
  - `plugin:development` scope
  - `pnpm run seed -- <plugin-path> --org <organization-id>`
  - An organization administrator

There is no contributor-facing publish command, public upload credential,
quarantine bucket, reviewer queue, submission endpoint, or `plugin:publish`
scope in the adopted model.


Bottom line
-----------

Other platforms commonly accept built artifacts through a marketplace UI or
API. ClassroomIO deliberately uses a different, source-first model at its
current scale: review a pull request, rebuild it in protected CI, publish only
digest-qualified immutable assets, and record the commit and workflow run with
the catalog version.
