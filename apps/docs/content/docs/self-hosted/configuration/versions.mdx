---
title: Versions & upgrades
description: Pin CIO_VERSION, upgrade ClassroomIO safely, and roll back to a previous release.
---

ClassroomIO publishes versioned images. `CIO_VERSION` controls which tag you run.

## Choosing a tag

- **Pin an exact release** (e.g. `1.0.0`) in production, so a merge to `main` never restarts you onto
  changed images unattended.
- `latest` is the freshest `main` build: it moves on **every merge** (rolling; may include unreleased
  code). The version tags (`1.0.0`, `1.0`, `1`) are the immutable, pinned releases.

```zsh title=".env"
CIO_VERSION=1.0.0   # pin a release; blank or "latest" = rolling main build
```

:::note[Confirm the tag exists]
Before deploying, confirm the tag you set actually exists at
[hub.docker.com/r/classroomio](https://hub.docker.com/r/classroomio/).
:::

## Upgrading

### Pre-built images (Docker)

```zsh title="Terminal"
./classroomio.sh upgrade
```

The script [backs up](/self-hosted/backups) Postgres and MinIO first, lets you pin a new
`CIO_VERSION`, then re-pulls and recreates. Running compose by hand is equivalent (minus the
backup): bump `CIO_VERSION` in `.env`, then:

```zsh title="Terminal"
docker compose -f docker-compose.images.yaml --env-file .env --profile minio pull
docker compose -f docker-compose.images.yaml --env-file .env --profile minio up -d
```

### Build from source (Docker)

`git pull`, then re-run `./classroomio.sh upgrade --build` to rebuild. Like the pre-built path,
this backs up Postgres and MinIO first, then rebuilds and restarts. (`start --build` also
rebuilds, but skips the backup step — use `upgrade --build` when upgrading an existing
deployment with real data.)

### Railway / Coolify / Dokploy / DigitalOcean

Set `CIO_VERSION` to the newer release and redeploy (on a DigitalOcean-style VPS: `dc pull && dc up -d`).
Because you pin a version, a new release never restarts you onto changed images unattended.

### Upgrading from a pre-Cohorts deployment

Schema migrations run automatically when the API starts (see the warning below). If your deployment
predates the Cohorts feature, though, it may still have data in the legacy `program` tables. That data does
**not** move itself. After the automatic schema migration has applied, run this one-time script to copy it
into the new cohort tables:

```zsh title="Terminal"
docker compose --env-file .env -p classroomio -f docker-compose.images.yaml stop api dashboard jobs
docker compose --env-file .env -p classroomio -f docker-compose.images.yaml run --rm --no-deps --entrypoint pnpm api --filter '@cio/db' migrate:programs-to-cohorts
```

This copies existing data into the new tables without dropping the legacy `program` tables. Skip this step
entirely on a fresh install or any deployment that was already on Cohorts.

## Rolling back

Set `CIO_VERSION` back to the previous release and run the same upgrade command (or redeploy). Pinned
versions make rollbacks reproducible.

:::warning[Back up before upgrading]
Database schema migrations run **automatically** when the API starts. Back up your Postgres volume
(and object storage) before a major upgrade, and avoid `docker compose down -v` / `docker volume prune`,
which delete your data volumes.
:::
