The API limits how many requests each API key or OAuth connection can make, so one integration can't slow down the others.

## The limit

Each API key or OAuth connection can make **100 requests per minute**. Every key and connection has its own budget, so traffic on one doesn't use up another's.

## Rate limit headers

Every response tells you where you stand:

| Header | Meaning |
| --- | --- |
| `X-RateLimit-Limit` | Requests allowed per minute |
| `X-RateLimit-Remaining` | Requests left in the current minute |
| `X-RateLimit-Reset` | When the current minute ends, as an ISO 8601 timestamp |

```http
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 87
X-RateLimit-Reset: 2026-10-23T14:05:00.000Z
```

## Exceeding the limit

Once you go over the limit, requests fail with `429 Too Many Requests` until the minute resets. The `Retry-After` header and the `retryAfter` field both give the number of seconds to wait.

```json
{
  "error": "Too Many Requests",
  "message": "Rate limit exceeded. Please try again later.",
  "retryAfter": 42
}
```

This body is shaped differently from [other errors](/api/errors): it has no `success` or `code` field.

### MCP keys

MCP usage also has per-minute limits for each connected app or MCP key (`cio_mcp_...`) and for the whole organization. Going over them returns a `429` in the [standard error format](/api/errors#error-format), with no `Retry-After` header and no `retryAfter` field:

```json
{
  "success": false,
  "error": "Automation rate limit exceeded",
  "code": "AUTOMATION_RATE_LIMIT_EXCEEDED"
}
```

Wait up to a minute, because the limit counts the last 60 seconds, then retry.

### Zapier connections

Requests from the ClassroomIO Zapier app use the same limit as every other public API client: **100 requests per minute for each connection**. Over the limit, the API returns `429` with `Retry-After`, and Zapier retries the step.

### Course invites

Creating course invites has a separate limit: each person can create invites for one course 60 times in any hour. For an API key or connection, that person is whoever created the key or connected the app. The dashboard, `POST /courses/{courseId}/invites` and `POST /courses/{courseId}/enrollments` share this budget. Every `/invites` request counts. An `/enrollments` call counts only when it has to send a new invite, so a repeat call that returns `already_enrolled` or `already_invited` doesn't.

Over the limit, `/invites` answers with the per-key body shown above, with `Retry-After`. `/enrollments` answers in the [standard error format](/api/errors#error-format) with `code` `COURSE_INVITE_RATE_LIMIT_EXCEEDED` and no `Retry-After`. Wait and retry later.

## Handle a 429

Wait for `Retry-After` seconds, then retry. When the header is missing, as it is for MCP usage limits, this waits 60 seconds:

```js
async function request(url, options) {
  const res = await fetch(url, options);

  if (res.status === 429) {
    const seconds = Number(res.headers.get('Retry-After') ?? 60);
    await new Promise((resolve) => setTimeout(resolve, seconds * 1000));
    return request(url, options);
  }

  return res;
}
```

To stay under the limit:

- Watch `X-RateLimit-Remaining` and slow down before it reaches zero.
- Use the largest page size you need (`limit` up to `100`) instead of many small pages. See [Pagination](/api/pagination).
- Cache responses that don't change often.

:::note[Self-hosted instances]
Rate limits apply only when the API runs with `NODE_ENV=production` and can reach Redis. If Redis is unavailable, most requests go through without a limit. Creating course invites through the public API is the exception: `POST /courses/{courseId}/invites`, and `POST /courses/{courseId}/enrollments` when it needs a new invite, fail with `503` and `code` `RATE_LIMIT_UNAVAILABLE` until Redis is back.
:::
